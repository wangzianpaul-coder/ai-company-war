## Architecture Boundary

### Six-quarter lifecycle and commands

- `GameSession` remains the UI's only business entry and accepts the same exact three player commands. Do not add campaign, report, batch, Market, AI, GTM, price or focus commands.
- A session records its starting elapsed month and derives a committed Prototype count from successful three-month advances. The valid range is `0..6`; six quarters are exactly 18 months.
- Start Project and Set Compute Allocation keep their accepted semantics. Only a successful Advance Quarter appends a report and increments the Prototype count.
- A failed Advance or any command after completion changes no active state, opponent state, named RNG, cached planning snapshot/preview, report history or published signal count.
- The existing cached opponent snapshot/privacy rule, stable candidate order, exact shared Compute legality and `ai`-only RNG consumption remain unchanged for all six quarters.
- Successful quarters 1–5 atomically replace the cached observable snapshot and non-consuming next preview. Quarter 6 retains the committed boundary snapshot but does not generate or expose a Q7 decision: it clears the cached preview, publishes the primitive text `Prototype complete — no next signal`, and encodes every next field as `-`.

### Quarter Report ownership

- `QuarterReportBuilder` is a pure simulation-domain transformer. It may read deep copies of the pre-quarter state, successful `TickResult`, ordered contributions, committed opponent metadata and non-consuming next signal; it may not mutate any input or rerun economic systems.
- Build and validate the report before GameSession publishes the successful quarter. If report construction or reconciliation fails, the whole application transaction is rejected and the active session remains unchanged.
- `QuarterReport` owns immutable primitive facts, stable keys and deep-copied contributions. It never stores UI nodes, mutable active state, a Session reference or a future Command.
- Each report metric has one explicit contribution mapping. Cash accepts cents contributions to `cash_cents` from Finance monthly revenue/operating cost with Company subject and Project monthly cost with the stable project subject. Company monthly revenue is the deliberate composite: Project completion contributions to `monthly_revenue_cents` plus Consumer and Developer/API Market revenue-change contributions to `market_monthly_revenue_cents`. Consumer/Developer share and revenue accept only that market subject's share-change/pressure bps or market-revenue cents. Player training/served/unmet accept only Company-subject Compute contributions for the corresponding cumulative compute-unit-month metric. Northstar Compute contributions never enter a player metric; its action is reported separately from committed opponent metadata.
- For each report metric, sum every contribution admitted by its mapping and require that sum to equal the primitive before/after delta. This includes the composite Company revenue mapping and actual post-clamp market deltas. The derived `outside_share_bps := 10000 - player_share_bps` is an invariant/display primitive only, never a new opponent/outside ledger.
- Select at most three displayed reasons from the full mapped set by descending absolute delta, then original contribution order, then source/reason/subject/metric stable keys. Never rank cents against bps or unit-months. Displaying only three reasons must not change the full reconciliation proof.
- Opportunity cost is an observed committed fact: training work alongside served/unmet inference. Known risk may use current unmet inference and the cached next rival signal, but no hidden forward simulation or unlabelled prediction.
- Application maps reports into `QuarterReportViewModel` objects containing only strings, integers, booleans and copied primitive arrays. UI reads these ViewModels and performs navigation only; it imports no simulation report/state/system/engine/event/AI/RNG type.

### Batch isolation and determinism

- `SixQuarterBatchSimulator` is a pure headless debug service. Production code must not depend on `debug/` or `tests/`; the service may depend on Application and Simulation public APIs.
- Each run constructs a fresh, fully independent state, personality, Engine and GameSession. No RefCounted state, report, contribution array, personality candidate or RNG object may be shared mutably across runs.
- Every run uses the real Start Project, Set Compute Allocation and Advance Quarter commands through `GameSession`; the batch may not call Systems directly, set private state, skip report construction or discard a failed run.
- The batch performs the exact two policies and seed order in Deterministic Golden Rules. It consumes only each run's `ai` stream; each initialized `events` and `market` stream must remain bit-for-bit unchanged for the complete game.
- Aggregation uses stable run order and integer facts. No global random function, system time, frame delta, filesystem enumeration, network, thread completion order, object ID or `hash()` may affect a result.
- Canonical digest input has an explicit version and field order. It contains every run's seed, policy, six report summaries, terminal state facts and errors; SHA-256 is applied only after canonical UTF-8 lines are complete.

### Atomic publication and UI

- For successful quarters 1–5, state, contributions, opponent decision/RNG, cached next preview, report history, Prototype status and the single committed signal become visible together. Quarter 6 atomically publishes the same committed facts plus completion/no-next-signal state, with no cached Q7 preview.
- Start/Set success, rejected/null/base/unknown/derived commands and failed quarters preserve the current report selection/history and do not emit a phantom report.
- Report navigation, drawer expansion and scrolling are presentation state only. They never submit a Command, change GameSession or affect batch/deterministic results.
- At 1280×720 and 1920×1080 the bounded summary/detail hierarchy must coexist with RIVAL, MARKETS, COMPUTE and finance explanations without clipping or overlap. The UI must remain player-facing and must not become a raw effect/debug dump.

- The canonical interactive run uses `NamedRngState.create_fresh_version_one(7)`. Batch run seed `s` uses the same exact fixture except `create_fresh_version_one(s)`; for seeds `1..50`, initial `ai/events/market` states are `s/s+4/s+6`, and the latter two must be identical at the end.
- It submits Start Project once before quarter 1. For each of six quarters it submits exactly one legal Set Compute Allocation followed by one Advance Quarter.
- The canonical interactive training schedule is `[40, 40, 40, 40, 40, 40]`. It produces exactly six reports and advances exactly 18 months; the implementation test must pin the complete terminal primitive state and each report's metric/reason order as explicit reviewed Goldens.
- The 100-game batch iterates stable lowercase policy key first, then seed: `training_first` for master seeds `1..50`, followed by `inference_first` for master seeds `1..50`.
- `training_first` uses training allocations `[70, 70, 40, 40, 20, 20]`; `inference_first` uses `[20, 20, 40, 40, 70, 70]`. Each game submits Start Project once, then six Set/Advance pairs.
- Thus the batch has exactly 100 fresh games, 600 successful quarters, 600 reports, 100 Start commands, 600 Set commands and 600 Advance commands. Any rejected command, missing/extra report or incomplete game fails the entire batch result.
- Each market always satisfies `player_share_bps + outside_share_bps = 10000`, where outside share is derived as `10000 - player_share_bps` and is not stored as another ledger. All shares are within `0..10000`; money, workload, training/inference and contribution reconciliation remain valid integers without overflow.
- Canonical digest text is UTF-8 with LF only and one final LF. It begins with `acw-tp023-batch-v1`. For each run in policy/seed order it writes one `run` line followed by six quarter-ordered `report` lines, using ASCII `|` delimiters, decimal integers without grouping and stable StringName values without display text.
- Each `run` line has this exact field order: ordinal, policy, seed, status, error key, quarter count, report count, elapsed months, cash, Company monthly revenue, player training/served/unmet totals, Consumer share/revenue, Developer/API share/revenue, and final ai/events/market stream states. Each `report` line has: run ordinal; quarter; start/end elapsed months; before/after cash, Company revenue, Consumer share, Consumer revenue, Developer/API share, Developer/API revenue, player training, player served and player unmet, in that exact order; committed rival candidate/training/reason/base/noise/total; next candidate/training/reason; and the displayed stable reason keys in displayed order. The final `aggregate` line has games, quarters, reports, failures, `training_first` count and `inference_first` count, in that order.
- Encode status only as `ok` or `error`. Encode an absent error, quarter-6 next field or empty reason list as `-`; otherwise every key must match `^[a-z0-9_]+$`, so no escaping is permitted. Multiple displayed reason keys use comma in existing displayed order. Any value that cannot satisfy this grammar fails the batch before hashing.
- Hash the complete canonical text with SHA-256 and print lowercase hexadecimal. Run A and an independently rebuilt Run B must match every canonical line, aggregate and digest byte-for-byte. The digest is reproducibility evidence, not a substitute for explicit state/report Goldens and invariant assertions; do not bless one runtime output as its own semantic oracle. Record the observed digest and exact aggregate facts in the completion report.
- Candidate order, report contributor order, policy order, seed order and digest field order are stable and never derived from Dictionary or filesystem enumeration.
