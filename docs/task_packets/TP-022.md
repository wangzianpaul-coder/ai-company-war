## Architecture Boundary

### Observable planning snapshot and fairness

- `OpponentPlanningSnapshot` is a typed immutable-by-interface `RefCounted` with exactly three primitive fields: `elapsed_months`, `consumer_player_share_bps` and `developer_api_player_share_bps`.
- It exposes no GameState, Company, Project, Market, player Compute, current player Command, mutable object or hidden cash/revenue field.
- GameSession caches the snapshot at session initialization. Successful Start Project and Set Compute Allocation commands do not refresh it or the already published opponent signal.
- On Advance Quarter, Engine first requires the cached snapshot's elapsed month and two share values to exactly equal the committed GameState Clock/Market boundary, and requires opponent/personality IDs to match. It then recomputes the actual decision from that cached snapshot plus committed private opponent/RNG state; it never trusts a UI preview object. A stale/forged month, share or ID is typed atomic failure.
- Only after a complete successful quarter does GameSession cache the next snapshot and publish the next signal. Failure preserves state, opponent memory, all RNG streams, snapshot, signal, effects, ViewModel and signal count.

### Opponent, personality and legal command

- `OpponentState` is typed, fully copied and owns one stable fictional ID, an independent ComputeState and last committed candidate/action/reason/base/noise/total metadata. The fixed ID is `&"northstar_labs"`; the display name is `Northstar Labs`.
- The active demo opponent Compute configuration is total `100`, reserve `10`, workload `50`, initial training allocation `40`, and zero cumulative/current results before its first decision.
- `OpponentPersonality` is an immutable-by-interface injected `RefCounted`. Typed candidate records declared in that same script contain only `candidate_key`, `training_units`, `reason_key` and `utility_rule_key`; constructor inputs are copied and getters return primitives or copies. The profile also owns `defend_base_points`, `defend_share_divisor_bps`, `train_base_points` and `training_target_compute_unit_months`. No content registry or mutable Resource is introduced.
- Northstar's exact candidate/profile values are: `plan_40_defend_markets / 40 / defend_market_position / defend_markets`, `plan_70_close_training_gap / 70 / close_training_gap / close_training_gap`, and integer parameters `500 / 100 / 500 / 180` in the field order above. AiSystem supports exactly those two utility-rule keys in this slice and reads every scoring constant from the injected profile; unknown/duplicate rule or candidate keys are invalid.
- `AiSystem` receives only OpponentPlanningSnapshot, OpponentState, OpponentPersonality and a copied NamedRngState. It never receives GameState, CompanyState, ProjectState, player ComputeState or a player Command.
- Each candidate is the exact existing `SetComputeAllocationCommand`, not a derived script. Candidates are sorted by stable candidate key, filtered on an OpponentState Compute copy through the existing `ComputeSystem.set_training_allocation`, then scored.
- Every legal candidate consumes exactly one AI-stream draw in stable order. No legal candidate means typed failure with no RNG consumption or mutation.

### Versioned named RNG

- `NamedRngState` stores master seed, algorithm version and separate `ai`, `events` and `market` integer stream states. Full copy and validation cover every field. The active algorithm version is exactly `1`; active master/stream values are each in `[1,2147483646]`.
- Fresh version-1 initialization accepts a master seed in that same range and derives streams exactly as `ai = master`, `events = 1 + ((master - 1 + 4) mod 2147483646)` and `market = 1 + ((master - 1 + 6) mod 2147483646)`. Thus master `7` produces `7 / 11 / 13`. The checked current-state constructor used by copy/quarter commit accepts independently advanced valid stream values and does not rederive them.
- TP-022 consumes and commits only the `ai` stream. `events` and `market` states remain bit-for-bit unchanged and are not connected to EventSystem or Market randomness.
- Algorithm version 1 is Park–Miller with state range `[1,2147483646]`, multiplier `48271`, modulus `2147483647`, `next_state = state × 48271 mod 2147483647` and bounded noise `next_state mod 10`.
- The maximum multiplication is representable in signed 64-bit. Invalid version/state is typed failure before any commit.
- Global `rand*`, `RandomNumberGenerator`, float, Time, frame delta, `hash()`, instance ID, directory order and thread completion order are forbidden.

## Deterministic Golden Rules

Stable candidate order and reasons:

```text
plan_40_defend_markets       → training 40 → defend_market_position
plan_70_close_training_gap   → training 70 → close_training_gap
```

All calculations are checked integers and read the named parameters from OpponentPersonality:

```text
defend_base = defend_base_points
             + floor((consumer_player_share_bps
                    + developer_api_player_share_bps) / defend_share_divisor_bps)
train_base  = train_base_points
             + max(0, training_target_compute_unit_months
                    - opponent_cumulative_training_compute_unit_months)
total       = base + noise
noise       = next_ai_rng_state mod 10
winner      = highest total, then candidate_key ascending
```

The top reason is the winning candidate's non-random reason; noise is never a reason.

Fixed demo inputs are the Northstar profile parameters `500 / 100 / 500 / 180`, public shares `3000 / 2000`, opponent cumulative training `0`, and a fresh version-1 NamedRngState from master seed `7`, which gives AI state `7`, events state `11` and market state `13`.

- First two bounded noise values are `7` and `8`; after their Park–Miller state transitions the proposed next AI state is `1278240558`.
- Plan 40 is `550 + 7 = 557`; plan 70 is `680 + 8 = 688`.
- The first decision is exact plan 70 with `close_training_gap`.
- Under a player default-training-40 quarter, opponent monthly totals are training `70`, inference served `20/50` and unmet `30`.
- Opponent quarterly totals are training `210`, served `60/150` and unmet `90`.
- Consumer opponent service is `12/month`, pressure `-24 bps/month`, quarter total `-72`; Developer/API service is `8/month`, pressure `-40 bps/month`, quarter total `-120`.
- Player organic quarter totals remain `+90 / +30`. Final shares are `3018 / 1910`; final market revenues are `30180 / 85950`; Company monthly revenue is `146130`; cash is `1071130`.
- The active-opponent trace is exactly 52 contributions: the accepted default trace 37, plus nine opponent Compute and six opponent-pressure contributions. There is no separate AI-decision contribution; command/reason/score remain OpponentState metadata.
- Per month order is Project, player Compute, opponent Compute, Finance, then Consumer served/organic share/opponent pressure/revenue and Developer/API in the same order, then Clock.

After that successful first quarter, the committed AI state is still exactly `1278240558`. The next boundary preview uses public shares `3018 / 1910`, opponent cumulative training `210` and a copy of that committed AI state:

- preview noise values are `4 / 7` and its proposed next AI state is `518142577`;

Displaying that preview must not mutate the committed RNG. State `518142577` is committed only if the next `AdvanceQuarterCommand` successfully recomputes and commits that same decision; a failed next quarter leaves committed state `1278240558`.

Stable-tie oracle: AI state `10` produces initial noises `0 / 0`; public shares `0 / 0` and opponent cumulative training `180` give both bases `500`, so candidate-key order must choose plan 40.
