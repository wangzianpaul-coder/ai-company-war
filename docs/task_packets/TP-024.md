## Deterministic Golden Rules

The catalog order and formulas below are part of TP-024's deterministic prototype contract. All division rounds toward zero on non-negative operands, equivalent to mathematical floor. All operands and intermediate products require explicit signed-64-bit overflow checks. Share changes are applied sequentially and clamped to `[0, 10000]`; each contribution records the actual post-clamp delta, not the requested value.

For each of the three months, after player Compute and Northstar Compute have settled and inside the existing Market settlement:

1. Apply existing served/unmet and base organic share change.
2. In catalog order, apply selected non-defense Focus share changes:
   - `model_quality_sprint`: for both markets, `training_allocation_units_per_month / 5` bps; zero when training work is zero.
   - `service_reliability_drive`: separately per market, `served_units * 10 / workload_units` bps; zero when workload or served is zero and never above 10 bps.
   - `consumer_growth_push`: Consumer `served_units * 20 / workload_units` bps; zero when workload or served is zero and never above 20 bps.
   - `developer_ecosystem_push`: Developer/API `served_units * 20 / workload_units` bps; zero when workload or served is zero and never above 20 bps.
3. Apply the existing full actual opponent-pressure delta.
4. If `defend_market_position` is selected, recover separately in each market `pressure_magnitude * 2500 / 10000` bps, capped at that same month's actual pressure magnitude; zero when pressure is zero. Defense never cancels an opponent command or changes opponent Compute.
5. Derive both market revenues and composite Company monthly revenue from the final shares and actual service using the existing Market formula.

For each market and month, preserve the existing served then unmet contribution order, followed by base organic share, selected Model Quality, selected Service Reliability, the applicable selected Growth action, actual opponent pressure, selected Market Defense recovery, then market revenue. Omit zero-delta contributions but retain all three committed Focus IDs in the report so a selected zero-effect action remains explainable. Use `SOURCE_EXECUTIVE_FOCUS` and one stable reason key per action; share contributions use the existing market subject, `METRIC_PLAYER_SHARE_BPS` and `BASIS_POINTS`.

Plan input order is not strategic. Every one of the six permutations of the same three IDs must canonicalize to the same stored plan and produce identical state, contribution order, report primitives, ViewModel, RNG and canonical batch bytes.

The old null-catalog/null-plan path must retain every TP-023 Golden exactly, including the old normal runner, 52-item active Q1 trace, six-quarter terminal state, 100-game canonical lines and digest. Focus never consumes `ai`, `events` or `market` RNG; the rival continues to consume only its accepted `ai` draws.
